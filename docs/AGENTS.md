# Agent Instructions

This file tells any AI coding agent how to work inside the HackStop project. Read it before writing a single line of code.

HackStop is a self-hostable hackathon submission and judging platform built with Next.js, TypeScript, PostgreSQL, and Prisma. It runs entirely inside Docker. It is our submission to the Dogfood 2026 hackathon.

---

## Before You Start

Read these files in this order before writing or changing any code:

1. `docs/PRD.md` -- what we are building, who it is for, every feature, every acceptance suite check.
2. `docs/DESIGN_SYSTEM.md` -- colors, typography, spacing, component rules. Follow them exactly.
3. `ARCHITECTURE.md` -- system overview, directory layout, request flow, auth, role isolation, Docker setup.
4. `DATA-MODEL.md` -- every database table, columns, constraints, fixture data edge cases, import/export paths.
5. `JUDGING.md` -- judge assignment, scoring rubric, z-score normalization formula, edge case handling, worked examples.
6. `docs/fixtures.json` -- the actual fixture data. 1 event, 8 tracks, 30 judges, 40 teams, 41 projects, 126 scores.
7. `docs/spec.md` -- the official hackathon specification. The acceptance suite contract.
8. `docs/run.py` -- the acceptance checker source. Read it to understand exactly what HTTP requests it makes and what responses it expects.
9. `prisma/schema.prisma` -- the current database schema. Always check it before creating or modifying tables.

Inspect existing components, utilities, and API routes before creating new ones. Duplication is a bug.

## General Rules

- Use TypeScript for everything. No plain JavaScript files.
- Use the Next.js App Router (not Pages Router). All routes go under `src/app/`.
- Reuse existing components. Check `src/components/` before creating a new one.
- Keep components modular. One concern per file.
- Follow the existing folder structure. Do not reorganize directories without explicit approval.
- Do not add new dependencies unless strictly necessary. Every new dependency is a risk to the Docker build and offline operation.
- All database access goes through Prisma. No raw SQL unless Prisma cannot express the query.
- All timestamps are UTC. Use `TIMESTAMPTZ` in the schema and ISO 8601 strings in the API.
- All IDs are UUIDs generated by the database. Fixture IDs (evt_01, trk_01, etc.) go in the `external_id` column.
- Do not use `any` type in TypeScript. If a type is unknown, define it.
- Do not leave `console.log` in production code. Use structured logging if needed.
- Do not hardcode credentials, ports, or URLs. Use environment variables.
- Every API route must handle errors and return appropriate HTTP status codes.
- Every API route that requires auth must check the session and role before doing anything else.
- Do not use `try/catch` that silently swallows errors. Always return a meaningful error response.
- When the fixture data has an edge case (constant judge, duplicate submission, incomplete batch), handle it explicitly. Do not let it crash or produce wrong results.

## Code Guidelines

### Components

- Use React Server Components by default. Use `"use client"` only when the component needs browser APIs, state, or event handlers.
- Component files use PascalCase: `ProjectCard.tsx`, `ScoreForm.tsx`.
- Props types are defined in the same file as the component, above the component definition.
- Do not use `React.FC`. Use plain function declarations with typed props.
- Keep components under 200 lines. Extract sub-components if they grow larger.

### API Routes

- API route files go under `src/app/api/` following Next.js App Router conventions.
- Each route file exports named functions: `GET`, `POST`, `PUT`, `DELETE`.
- Every route that requires authentication must call `getSession()` first and return 401 if no valid session.
- Every route that requires a specific role must call `requireRole()` and return 403 if the role does not match.
- Judge routes must filter all database queries by the authenticated judge's user ID. Never return another judge's data.
- Return JSON with a consistent shape: `{ "data": ... }` for success, `{ "error": "message" }` for errors.
- Use appropriate HTTP status codes: 200 for success, 201 for creation, 400 for bad input, 401 for no auth, 403 for wrong role, 404 for not found, 409 for conflict, 500 for server errors.

### Naming

- Files and folders use kebab-case or the Next.js convention (e.g., `[eventId]` for dynamic routes).
- Database table names use PascalCase in the Prisma schema (Prisma convention).
- API response fields use snake_case to match the fixture data format.
- TypeScript types and interfaces use PascalCase.
- Variables and functions use camelCase.
- Constants use UPPER_SNAKE_CASE.

### Prisma

- The schema file is `prisma/schema.prisma`. It is the single source of truth for the database.
- Run `npx prisma migrate dev --name <description>` to create migrations during development.
- Run `npx prisma migrate deploy` in the Docker entrypoint for production.
- Run `npx prisma generate` after schema changes to update the TypeScript client.
- Use relations and `include` for eager loading. Avoid N+1 queries.
- Use transactions for operations that modify multiple tables.

## Design Rules

- Follow `docs/DESIGN_SYSTEM.md` for all visual decisions: colors, fonts, spacing, component styles, responsive breakpoints.
- Use Tailwind CSS utility classes. Do not write custom CSS unless Tailwind cannot express it.
- Use the defined color tokens as Tailwind config values. Do not hardcode hex colors in component files.
- All interactive elements must have visible focus states for accessibility.
- All form inputs must have labels. Do not use placeholder text as the only label.
- Error messages must be visible and specific. "Something went wrong" is not acceptable.
- Loading states must be visible. Do not leave the user staring at a blank screen.
- Empty states must have a message. An empty table with no explanation is confusing.

---

## Security Rules

- Never expose API keys, database credentials, or session secrets in client-side code.
- All secrets go in environment variables, defined in `.env` (gitignored) and `docker-compose.yml`.
- Passwords are hashed with bcrypt before storage. Never store plain text passwords.
- Session tokens are cryptographically random hex strings. Never use predictable values (except the four deterministic tokens created by the seed script for the acceptance suite).
- Validate all user input on the server side. Client-side validation is a convenience, not a security measure.
- Verify authorization server-side on every request. The role check lives in the API route handler, not in the middleware alone.
- Judge score queries always filter by authenticated user ID. There is no code path that returns another judge's scores.
- The peer-score route explicitly checks whether the requested judge ID matches the authenticated user and returns 403 if not.
- Deadline enforcement checks the current UTC time against the event's `submissions_close` timestamp on every submission and edit request.

```

npm run dev                          # Start development server
npm run build                        # Production build

npx prisma migrate dev --name <name> # Create a migration

docker compose up                    # Start the full stack (production)
docker compose up --build            # Rebuild and start
docker compose down                  # Stop everything
python3 docs/run.py .dogfood.toml    # Run acceptance suite
```

## Boundaries

Do not do any of the following without explicit approval:

- Change the tech stack (Next.js, PostgreSQL, Prisma, Tailwind).
- Add a new external dependency that makes network calls at runtime.
- Change the database schema in a way that breaks fixture seeding.
- Change the API route paths declared in `.dogfood.toml`.
- Remove or weaken role isolation checks.
- Change the normalization formula.
- Remove edge case handling for constant judges, duplicate submissions, or incomplete batches.
- Modify the Docker Compose configuration in a way that requires network access.
- Delete or restructure the `src/`, `prisma/`, `tests/`, or `docs/` directories.
- Change the session token format used by the acceptance suite.

## Testing Priorities

When in doubt about what to test, prioritize in this order:

1. Role isolation: Judge B cannot get Judge A's scores. Participant cannot access judge routes.
2. Deadline enforcement: Submissions are refused after the close date.
3. Fixture seeding: All 41 projects, 30 judges, 126 scores load correctly.
4. Normalization: Constant judges produce z=0, duplicates are excluded, rankings are correct.
5. Gallery: Public access, fixture titles visible in response body.
6. CSV export: Returns 200 with valid CSV for organizer, returns 401/403 for others.
